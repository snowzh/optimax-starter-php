# E2E 全功能覆盖（Playwright）

## 背景与目标

starter-scaffold 已验收（Pest 41 + E2E 11 + compose 冒烟全绿），但 2026-11 实测暴露「创建用户失败」：web 容器 nginx `try_files $uri/` 命中 exportStatic 目录触发 301，且 Location 基于 `$host`（不含端口）生成，宿主浏览器经 `127.0.0.1:8080` 直达/刷新任意路由页被弹到 80 端口直接连接拒绝。**compose 网络内 E2E 因 `http://nginx`（内部 80 = 默认端口）对该缺陷完全免疫**——测试全绿而人工使用全崩，构成系统性盲区。

本次将基座全部功能面收敛为 Playwright E2E 门禁，并补上「宿主端口直达」这一缺失维度，使「人工浏览器可用性」进入 CI 可回归的验收范围。

完成后对两类角色产生价值：开发者获得覆盖认证/RBAC/三管理页的回归防线（改坏即红）；运维获得宿主直达冒烟门禁，避免再次出现「容器内绿、宿主挂」的假验收。

## 用户故事

- 作为**开发者**，我希望 CI 中跑全功能 E2E，以便任何破坏认证、权限矩阵或管理页交互的回归在合并前被拦截。
- 作为**开发者**，我希望宿主端口直达各路由有冒烟断言，以便 nginx/路由层配置回归不再依赖人工发现。
- 作为**超管**，我希望用户/角色/权限管理的每项交互（含角色分配、启停、筛选、矩阵变更、直授抽屉）都有自动化验证，以便后续业务开发不改坏基座能力。

## 验收标准（EARS 语法，每条可独立验证）

### 宿主端口直达回归（本次事故防线）

- 当浏览器直接访问入口映射端口的任意前端路由（`/`、`/user/login`、`/system/user`、`/system/role`、`/system/permission`）时，系统返回 200 且**不发生任何 301/302 重定向**（服务端行为，以 compose 宿主 curl 断言 + 网内浏览器 `redirectedFrom` 断言双重收口）。
- 当浏览器携带尾斜杠访问 `/user/login/` 时，系统回退 index.html 交由前端路由处理，页面正常渲染登录表单。

### 认证

- 当已禁用用户尝试在 UI 登录时，系统展示 4002「用户已禁用」提示且停留登录页。
- 当会话携带无效 token 访问受保护页面时，系统清除本地 token 并跳转登录页（携带 redirect 参数）。

### 用户管理（/system/user）

- 当超管创建用户并分配角色时，系统在新行展示该角色的显示名 Tag。
- 当超管编辑用户显示名时，系统更新行内显示且不改动用户名。
- 当超管重置用户密码后，系统使旧密码失效、新密码可登录（以 API 登录断言）。
- 当超管切换用户启停开关时，系统即时更新状态列。
- 当超管提交已存在的用户名时，系统展示 3002 唯一性冲突提示且弹窗不关闭。
- 当超管提交两次不一致的密码时，系统行内提示且不发请求。
- 当超管按关键字/状态筛选时，系统表格仅展示匹配行。

### 角色管理（/system/role）

- 当超管创建角色并勾选权限矩阵时，系统在新行展示权限码 Tag。
- 当超管编辑角色显示名时，系统更新行内显示。
- 当超管删除自建角色时，系统移除对应行。
- 当查看受保护角色（super-admin）时，系统将其删除入口置灰不可触发。
- 当为角色勾选 `system.user.view` 后，挂该角色的用户登录时可见「系统管理 → 用户管理」子菜单项（角色权限 UI 链路端到端）；勾选前该子菜单项不渲染。

### 权限清单与直授

- 当超管访问权限清单页时，系统只读展示全部权限码且无操作入口。
- 当超管经直授权限抽屉为用户勾选 `system.user.view` 并保存后，该用户登录可见用户管理子菜单项；撤销后该子菜单项不再渲染（「系统管理」父项为体验层入口保留，无权限点击由路由 access 拦截兜底）。

## 完成标准

**影响面**：仅测试资产与 CI——`apps/web/e2e/`（新增 helpers 与 4 个 spec 文件、迁移 1 个用例）、`playwright.config.ts` 不变、`.github/workflows/ci.yml` compose job 增加宿主端口直达 curl 断言步骤。**不改任何业务代码**（本次发现的 nginx `try_files` 与 `redirectGuestsTo` 修复属 starter-scaffold 缺陷修复，另行提交，本 spec 仅为其建立回归防线）。

**测试方式**：全部用例在 compose 网络内执行（`docker compose --profile e2e run --rm e2e`），真实 API 禁 mock；测试数据自建自清（唯一前缀 + finally 清理），保证可重复执行；宿主直达断言由 CI compose job 在 runner 宿主端口 curl 收口。

**不做什么**：不做前端密码修改 UI 用例（当前无入口，API 层由 Pest ChangePassword 覆盖）；不做负载/并发压测；不做视觉回归比对（截图证据已有 evidence.spec.ts）；不测最后一个超管保护等纯后端规则的 UI 分支（Pest 已覆盖 4004/4005/4006）。
