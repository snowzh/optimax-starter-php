# 原料管理系统（material-mgmt）· 需求梳理

> 状态：**specify 草稿，待人工评审**——本文件只梳理领域逻辑与验收标准，不含表结构/接口设计（plan 阶段产出 design.md）。六条原始需求逐条映射见「领域规则溯源」节。

## 背景与目标

基座（认证/RBAC/审计/Redis 队列/CI 门禁）已就绪，现引入首个业务实体：**简易原料管理系统**，覆盖「产品—零部件—库存—出入库—生产」闭环。完成后对两类角色产生价值：仓库管理员获得型号登记、按编号管理库存件、出入库流水与生产记录的可追溯台账；生产操作者获得按产品型号清单领件、一键完成「消耗零件 / 产出产品」的原子化生产操作。

## 领域概念（实体字典）

| 概念 | 英文实体 | 说明 |
|---|---|---|
| **产品型号** | Product（型号层） | 产品的「型号/规格」目录条目，如「X1 型输送机」。无库存数量概念，库存挂在实例层 |
| **零部件型号** | Component（型号层） | 零件的型号目录条目，如「M-200 电机」。同一零件型号可被多个产品型号使用 |
| **安装位置** | InstallPosition | 产品型号 ↔ 零件型号的**型号级对应关系表**（见下方「关键解读」） |
| **产品库存件** | ProductUnit（实例层） | 某型号产品的一件实物，**独立编号**（序列号），有库存状态 |
| **零件库存件** | ComponentUnit（实例层） | 某型号零件的一件实物，**独立编号**，有库存状态 |
| **出入库流水** | StockMovement | 针对库存实例的一次出入库动作记录（append-only 台账） |
| **生产记录** | ProductionRecord | 一次生产事件：消耗了哪些零件、产出了哪个产品 |

### 「安装位置」的关键解读（待评审确认）

原文：*「产品和零部件的型号由名叫"安装位置"的表确定对应关系」*。存在两种解读：

- **解读 A（推荐）**：安装位置是产品型号上的一等实体——每个产品型号有若干**命名位置**（如「左侧电机位」「主控板位」），每个位置绑定一个零件型号。表结构即「产品型号 × 位置名 × 零件型号（× 用量）」。
  - 优点：语义完整（知道零件装在哪），同一位置天然不可重复绑定，BOM 展开直观
- **解读 B**：安装位置只是多对多联结表的名字，每行即「某产品型号 ↔ 某零件型号」，不承载位置语义。
  - 优点：更简易；缺点：同一产品对同一零件无法区分用途/位置，无法表达「位置 1 和位置 2 各装一个同型号零件」

本文档后续规则按**解读 A** 展示（对齐实际制造业心智），若你倾向 B，评审时说明即可，模型可平滑降级。

## 领域关系图（型号层与实例层分离）

```
            型号层（目录/配方）                      实例层（库存实物）
┌──────────┐   1    ┌──────────────────┐    ┌─────────────────┐
│ 产品型号  │───N───▶│  安装位置         │    │  产品库存件       │
│ Product  │        │  InstallPosition │◀───│  ProductUnit     │
└──────────┘        │ · 位置名称        │    │  · 型号 FK        │
      ▲             │ · 零件型号 FK     │    │  · 独立编号(唯一)  │
      │ N:1         │ · 用量(默认1,待定) │    │  · 库存状态       │
      │        ┌──────────────────┐    │    └────────┬────────┘
      │        │  零件型号         │◀───┘             │ 出入库流水 N:1
      │        │  Component       │◀──────────┐      │
      │        └──────────────────┘           │      │
      │                  ▲ 1                 ┌─┴──────▼─────────┐
      │                  │ N                 │ StockMovement    │
      │            ┌─────────────┐           │ · 方向(入/出)    │
      └────────────│ 零件库存件   │──────────▶│ · 类型(待定)     │
                   │ ComponentUnit│           │ · 时间/经手     │
                   │ · 独立编号    │           └─────────────────┘
                   │ · 库存状态    │
                   └──────┬──────┘
                          │ 生产消耗 N:1
                   ┌──────▼───────────┐
                   │ ProductionRecord │
                   │ · 产品型号 FK     │
                   │ · 消耗的零件列表 │
                   │ · 产出的产品 FK  │
                   │ · 生产时间/操作人  │
                   └──────────────────┘
```

要点：

1. **两层分离**（你的需求 1/3/4）：型号层回答「是什么、由什么组成」；实例层回答「具体哪一件、现在在哪」。型号无数量，库存计数 = 该型号下「在库」实例数。
2. **多对多**（需求 1）：产品型号经安装位置关联多个零件型号；同一零件型号可出现在多个产品型号的位置上。
3. **生产语义**（需求 6）：`ProductionRecord` 同时落三类事实——消耗的零件实例（状态 → 已消耗）、产出的产品实例（创建并在库）、事件本身（谁/何时/什么型号）。

## 库存状态机（待评审）

```
零件实例 ComponentUnit：
  [入库] ──▶ 在库 ──[出库:领用/报废]──▶ 已出库 / 已报废
                └──[生产消耗]────────▶ 已消耗（不可逆，仅生产记录可回溯）

产品实例 ProductUnit：
  [生产产出/采购入库] ──▶ 在库 ──[出库:发货/报废]──▶ 已出库 / 已报废
```

规则：已出库/已消耗/已报废为终态，**不可再参与出库或生产**；生产消耗不走出入库流水（见下方「流水与生产的关系」）。

## 出入库流水与生产的关系（规则声明）

- 出入库流水 `StockMovement` 记录**一般出入库**：入库（采购入库/生产入库/退库）、出库（领用/发货/报废）——类型枚举在 design 阶段定稿。
- **生产消耗**不走 StockMovement：零件被生产消耗、产品被生产产出，均由 `ProductionRecord` 承载（同一事务改状态），避免双记账。流水表 append-only，禁止修改删除。

## 领域规则溯源（六条原始需求映射）

| # | 原始需求 | 落点 |
|---|---|---|
| 1 | 产品由多个零部件组成，一零件可属多产品 | 型号层经 InstallPosition 多对多（图示 ①②） |
| 2 | 型号对应关系由「安装位置」表确定 | InstallPosition（解读 A/B 待评审） |
| 3 | 同型号产品多件入库存，单独编号 | ProductUnit（型号内/全局唯一待定） |
| 4 | 同型号零件多件库存，单独编号 | ComponentUnit（同上） |
| 5 | 产品与零件都要出入库管理 | StockMovement 统一流水（方向+类型+实例 FK） |
| 6 | 生产记录：零件被消耗、产品被生产 | ProductionRecord（三事实同事务） |

## 用户故事

- 作为**仓库管理员**，我希望登记产品/零件型号并维护安装位置清单，以便建立产品配方。
- 作为**仓库管理员**，我希望按型号登记入库每一件库存并赋独立编号，以便实物与台账一一对应。
- 作为**仓库管理员**，我希望做出入库操作并留流水，以便库存变动可追溯。
- 作为**生产操作者**，我希望选定产品型号后系统自动列出所需零件型号与数量，以便按清单领件。
- 作为**生产操作者**，我希望一次提交完成「零件转已消耗 + 产品产出入库」的原子操作，以便库存与事实永远一致。
- 作为**管理者**，我希望查询任一型号的在库数与流水、任一生产记录的消耗明细，以便盘点与审计。

## 验收标准（EARS 语法，每条可独立验证）

### 型号与安装位置

- 当登记产品/零件型号时，系统保存目录条目并返回信封；编码重复返回 3002 唯一性冲突。
- 当为产品型号新增安装位置并绑定零件型号时，系统保存对应关系；同一产品型号**同一位置名**重复绑定时返回业务码拒绝。
- 当删除安装位置时，系统解除型号对应关系且不影响任何库存实例与历史生产记录。

### 库存与出入库

- 当零件/产品实例入库时，系统校验编号唯一（重复返回 3002），实例置为在库并写入入库流水，同一事务。
- 当对在库实例执行出库时，系统置终态并写入出库流水；对已出库/已消耗/已报废实例再出库时返回业务码拒绝。
- 当查询型号库存时，系统返回在库实例数、实例分页列表与出入库流水（服务端分页信封）。
- 当删除型号时，若其下存在任何库存实例，系统拒绝（业务码）；零库存型号允许删除（软删或硬删在 design 定稿）。

### 生产

- 当请求某产品型号的生产清单时，系统按安装位置展开返回「零件型号 × 用量 × 当前在库数」及可生产数量（瓶颈值）。
- 当提交生产时，系统在同一事务内：将所选零件实例置为已消耗、创建产品实例（编号唯一校验）置为在库、写入生产记录；**任一零件不可用（非在库/编号不存在）时整体拒绝并返回业务码**，无部分生效。
- 当生产所需零件在库量不足时，系统拒绝提交并返回缺口明细。
- 当查询生产记录时，系统分页返回记录及其消耗零件/产出产品明细。

### 权限与审计（对齐基座基线）

- 当无对应查看权限的用户请求上述任一接口时，系统返回 403/2003 并记审计。
- 当型号登记、出入库、生产提交、安装位置变更发生时，系统在同一事务写入审计日志（含经手人），敏感字段脱敏基线不适用（无凭据类字段）。

## 完成标准

**影响面**：`apps/api`（新迁移与模型/Repository/Service/Controller、新权限点、Scramble 文档、Pest）；`apps/web`（新管理页：型号目录、安装位置维护、库存台账、出入库操作、生产工单、流水查询；ProTable/ModalForm 范式沿用）；`specs/material-mgmt/`（design/tasks/converge）；`API_CONVENTIONS.md` 新错误码登记。

**测试方式（双重测试红线，2026-11-24 补充）**：每一项操作必须同时具备两重测试——**① 基于 Laravel 测试工具（Pest）的纯后端测试**（API 生效：信封结构、错误码、状态机、事务原子性，含 4007-4011 全分支）与 **② 基于 Playwright 的 E2E 测试**（真实浏览器页面功能与显示正常：行渲染、表单交互、错误提示文案、筛选与统计显示）。逐操作测试矩阵见 design.md「测试矩阵」节；E2E 走 compose 网内真实 API 禁 mock，数据自建自清。

**不做什么**：多仓库/库位、批次与有效期、供应商与采购单、成本与价格核算、库存盘点/调拨、BOM 多级嵌套（零件由零件组成）、生产工单排程/半成品、条码硬件对接、Excel 批量导入。

## 决策清单（2026-11-24 评审拍板）

| # | 问题 | 决策 |
|---|---|---|
| 1 | 安装位置解读 | **A 方案**（位置为一等实体：产品型号 × 位置名 × 零件型号 × 安装数量） |
| 2 | 安装位置用量 | **带「安装数量」字段**（默认 1，≥1；例：一个孔位需 3 个同型号垫片） |
| 3 | 实例编号规则 | **全局唯一；格式 = 型号编码 + 实例编码**（如 `P-001-0007`），唯一性由服务端校验，格式推荐不强制 |
| 4 | 产品采购入库 | 按推荐：**允许**（入库类型：采购入库 / 退库） |
| 5 | 出库类型 | 按推荐：**领用 / 发货 / 报废** |
| 6 | 生产范围 | **只做「零部件 → 产品」组装过程**（不做零件由零件组成/生产零件）；消耗的零件**由操作者按具体编号指定** |
| 7 | 权限粒度 | **四点细分**：product / component / stock / production 四域（各域 view + manage 对齐基座范式） |
| 8 | 一次生产产出 | 按推荐：**单件**（N 件 = 提交 N 次） |
| 9 | 型号删除 | 按推荐：**软删**（历史生产记录/流水引用完整性） |
